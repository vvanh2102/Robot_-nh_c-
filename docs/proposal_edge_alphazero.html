Adaptive Simulation-Budget Allocation for AlphaZero-MCTS on Heterogeneous Edge Hardware

Resource-aware game-tree search under real-time deadlines, evaluated on a Raspberry Pi Zero–to–PC hardware spread, for an embodied Gomoku-playing robot.

FieldEdge AI / Embedded Systems
Base systemRobot Gomoku (13×13), branch vuvananh_intergration

StatusDraft — for advisor review
01

Motivation

The applicant maintains a working robot that plays 13×13 Gomoku: a 3-DOF arm with vacuum gripper, an eye-in-hand camera, and a two-model YOLO perception pipeline feed a GomokuAIStrategy module offering both Minimax/Alpha–Beta and an AlphaZero/MCTS adapter (10 residual blocks, 40 filters, 200 simulations, 4 parallel branches). Compute is currently split informally across a PC, a Raspberry Pi 3, and a Jetson NX, with no policy governing which device runs the search or at what budget.

This asymmetry between available compute and a single fixed search configuration is the starting point for this proposal.

02

Research question

Given a fixed decision deadline — set by the robot's real pick-and-place cycle time — which combination of network size and MCTS simulation budget maximizes playing strength on a given device tier, and does a policy that adapts this combination per move outperform any single fixed configuration under the same average time budget?
03

Gap in prior work

Split-computing literature (Neurosurgeon, BottleNet, and 2024–2025 follow-ups) addresses layer-wise partitioning of a single streaming vision model between edge and cloud. It does not transfer directly to a periodic, single-shot search problem like AlphaZero-MCTS, where the unit of work is a full move decision rather than a video frame. The applicable literature is instead anytime-algorithm and resource-adaptive inference work — thinner for tree search on genuinely constrained hardware such as a Cortex-A single-board computer.

05

Proposed contributions

  • 01Strength–latency Pareto curves across network configurations (block/filter count, INT8 quantization) and all four device tiers, including a Cortex-A-only tier rarely reported in split/anytime-inference literature.
  • 02An adaptive simulation-budget policy that selects network size and simulation count per move from remaining decision time and board-state complexity, rather than the system's current fixed 200-simulation budget.
  • 03A deadline grounded in the real system: derived analytically from the robot's documented pick-and-place motion timing, not an arbitrary constant.
06

07

Work plan

Phase 1 — Baseline profiling
Run the trained checkpoint at varying network sizes and simulation budgets on each device tier; record latency, throughput, and memory to establish the raw Pareto surface.
Phase 2 — Adaptive policy design
Build a rule-based policy that selects configuration from remaining time and position complexity; extend to a learned policy if time allows.
Phase 3 — Self-play evaluation
Run adaptive vs. fixed-budget tournaments and Elo comparisons across configurations entirely through console / Virtual Play, under the analytically derived deadline.
08

Feasibility & existing assets

  • Trained AlphaZero checkpoint in hand
  • GomokuAIStrategy adapter exposing both Minimax and AlphaZero behind one API in repo
  • Virtual Play mode for AI-vs-AI testing without camera or robot in repo
  • Minimax depth 1–3 baseline for sanity-check comparisons in repo
  • Documented real pick-and-place motion timing, for deriving the deadline constant documented
  • Pi Zero, Pi 3, Jetson NX, and PC hardware available
09

Future work

The vacuum gripper carries no pressure feedback, so the system currently commits an AI move to game state without confirming the piece was actually picked up. A lightweight binary classifier reading the eye-in-hand camera after the lift step — gripped vs. empty, nothing else — could close that gap, but requires physical data collection distinct from this proposal's console-only evaluation. It is noted here as a natural next step, outside the present scope.
